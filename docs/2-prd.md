## 1. 개요

### 1.1 제품 비전
기간(시작·종료 일시)이 있는 할일을 개인별로 관리하고, 팀과 공유해 캘린더(월·주·일)에서 한눈에 보며, 누가 무엇을 바꿨는지 추적할 수 있는 웹 TodoList.

### 1.2 배경 / 해결할 문제
| 문제 | 해결 FR |
|------|---------|
| P1 개인별 인증 할일 관리 부재 | FR-01, FR-02, FR-03, FR-06, FR-07 |
| P2 기간 지정 관리 불가 | FR-04, FR-05 |
| P3 캘린더 통합 조회 불가 | FR-08 |
| P4 팀 일정 공유·관리 불가 | FR-09, FR-11 |
| P5 변경 추적 불가 | FR-10 |

### 1.3 목표 사용자
| 구분 | 설명 |
|------|------|
| 학생 | 과제·시험 등 기간이 있는 일정을 관리. 스터디·조별 과제 팀 공유 |
| 직장인 (20대–50대) | 업무 일정 관리, 팀 단위 일정 공유. 팀장은 관리자(R19)로 팀원 일정 관리 |

- 사용자 페르소나별 상세 시나리오는 작성하지 않는다(사용자 요청).

## 2. 목표 및 성공 지표

### 2.1 비즈니스 목표
- 동시 접속 사용자 1000명이 지연·오류 없이 사용할 수 있어야 한다.
- 2일 내(2026-11-04 수 – 11-05 목) 1인 개발로 핵심 기능(MVP, 4장 P0)과 P1을 완성한다(Q3).

### 2.2 부하 모델 **[확정]**
| 항목 | 값 | 근거 |
|------|----|------|
| 동시 접속 | 1000명 (가상 사용자 1000 VU) | 비즈니스 목표 |
| 사용자당 요청 간격(think time) | 평균 10초 (5–15초) | 할일 앱은 화면 조회 후 입력·확인에 시간이 걸린다 |
| 평균 처리량 | 약 100 RPS | 1000명 ÷ 10초 |
| 검증 처리량 | 200 RPS (평균의 2배) | 출근·수업 시작 시각 몰림 대비 |
| 요청 구성 | 조회(목록·캘린더) 70% / 쓰기(등록·수정·완료·삭제) 20% / 인증 10% | 일반적인 CRUD 앱의 읽기 위주 패턴 |

- 부하 테스트는 하지 않는다(Q2). 이 모델은 설계(커넥션·인덱스·페이지네이션, 5.1)의 근거로만 쓴다.

### 2.3 성공 지표 (KPI)
| ID | 지표 | 목표 | 측정 방법 | 근거 |
|----|------|------|-----------|------|
| M1 | 조회 API p95 응답시간 (목록·캘린더) | ≤ 500ms | 설계 목표. 부하 테스트 생략(Q2)으로 출시 전 실측하지 않음 | 사용자가 지연을 체감하지 않는 일반 기준 |
| M2 | 쓰기 API p95 응답시간 | ≤ 800ms | 동일 | 트랜잭션(이력 기록 등) 포함 |
| M3 | 로그인 API p95 응답시간 | ≤ 1500ms | 동일 | 비밀번호 해시 검증이 CPU를 쓴다(5.2) |
| M4 | 오류율 (5xx + 타임아웃) | < 1% | 동일 | 정상 부하에서 서버 오류는 예외적이어야 한다 |
| M5 | DB 커넥션 풀 대기 p95 | < 50ms | 동일 | 풀 크기(5.1)가 충분한지 확인 |
| M6 | P0 수용 기준 통과율 | Day 2 종료 시 100% | 4장 체크리스트 수동/자동 검증 | 2일 MVP 완료 정의 |
| M7 | 신규 가입자 중 24시간 내 할일 1건 이상 등록 비율 | ≥ 70% | DB 집계 | 핵심 가치(할일 등록) 도달 여부 **[확정]** |

- M1–M5 수치는 모두 **[확정]**이다. 단, 부하 테스트를 생략하므로(Q2) 1000명 동시 접속 달성 여부는 출시 전에 검증되지 않는다(K3).

## 3. 범위

### 3.1 In Scope
| 구분 | 내용 | FR / UC |
|------|------|---------|
| 인증 | 회원가입, 로그인, 로그아웃 | FR-01 / UC-01–UC-03 |
| 프로필 | 이름·비밀번호·시간대 수정 | FR-03 / UC-04 |
| 카테고리 | 본인 카테고리 CRUD, 기본 카테고리 | FR-02 / UC-05 |
| 할일 | 등록(시작·종료 일시), 수정, 완료·해제, 삭제 | FR-02, FR-04, FR-06, FR-07 / UC-06, UC-08–UC-10 |
| 조회 | 목록 필터(팀·사용자 / 카테고리 / 상태), 캘린더(월·주·일) | FR-05, FR-08 / UC-07, UC-11 |
| 팀 | 팀 생성, 구성원·역할 관리, 할일 팀 공유, 관리자 권한 | FR-09, FR-11 / UC-13, UC-14 |
| 이력 | 할일 변경 이력 기록·조회 | FR-10 / UC-12 |
| 플랫폼 | 웹, 모바일은 반응형 웹 UI | - |

### 3.2 Out of Scope
- 도메인 정의서 7장 전체(팀 삭제·소유자 위임·팀 나가기·초대 수락, 삭제 할일 이력·되돌리기, 알림·리마인더, 반복 할일, 종일/시간 구분, 우선순위·태그·하위 할일·첨부, 소셜 로그인·비밀번호 찾기·이메일 인증, 회원 탈퇴, 휴지통, 외부 캘린더 연동, 통계·리포트).
- PRD 추가 제외:
  - 네이티브 모바일 앱 (반응형 웹만)
  - 접근성(WCAG 등) 대응 (사용자 요청으로 고려하지 않음)
  - 다국어 (한국어 UI만) **[확정]**
  - 실시간 동기화(WebSocket 등). 다른 사용자의 변경은 새로고침·재조회 시 반영 **[확정]**

## 4. 기능 요구사항

### 4.1 우선순위 정의
| 우선순위 | MoSCoW | 의미 |
|----------|--------|------|
| P0 | Must | 2일 MVP. Day 2(11/05 목) 종료까지 완성 |
| P1 | Should | P0 완료 직후 구현. 목표일도 11/05(목)(Q3). v1.0 출시 전 필수 (모두 [확정] 요구사항이므로 Won't는 없음) |

### 4.2 우선순위 요약 **[확정]**
| FR | 우선순위 | 판단 이유 (한 줄) |
|----|----------|-------------------|
| FR-01 | P0 | 모든 기능의 전제(R1). 없으면 앱을 쓸 수 없다 |
| FR-02 | P0 | 할일은 반드시 카테고리에 속한다(R7). 할일 등록의 전제 |
| FR-04 | P0 | 기간 관리(P2)가 제품 핵심이고 상태·캘린더가 일시에 의존(R4) |
| FR-05 | P0 | 상태 판정(S1–S4)은 제품 차별점이며 목록 화면의 기본 기능 |
| FR-06 | P0 | 기본 CRUD. 구현량이 적다 |
| FR-07 | P0 | 기본 CRUD + 완료 처리(R14). 편집 화면은 등록 화면을 재사용 |
| FR-08 | P0 | 캘린더 조회(P3)는 핵심 가치. 라이브러리로 범위를 줄인다 |
| FR-11 | P0 | 이해관계자 결정으로 MVP에 팀 기능 포함(Q4). 팀 공유(P4)는 제품 차별점 |
| FR-09 | P0 | FR-11과 함께 MVP에 포함(Q4). 팀 생성·구성원 관리(UC-13, UC-14) 포함 |
| FR-03 | P1 | 시간대 기본값 KST로 MVP 사용에 지장 없음. 구현량은 작아 P1 1순위 |
| FR-10 | P1 | 할일 쓰기 경로 전체에 기록이 붙고 필드별 diff·가시성 규칙(R20)이 있어 P0 안정화 뒤 추가 |

- 데이터 모델은 P1까지 포함해 Day 1에 한 번에 만든다(TodoHistory 테이블 포함). P1 추가 시 마이그레이션 재작업을 피하기 위함 **[확정]**.
- 권한 조건(R2, R19, R21)은 처음부터 목록·캘린더·수정·삭제 쿼리에 넣는다. 개인용으로 먼저 만들고 나중에 고치지 않는다.

### 4.3 FR별 요구사항 및 수용 기준

#### FR-01 회원가입·로그인 (P0) — R1, R6, R16 / UC-01–UC-03
- [ ] 이메일·비밀번호·이름으로 가입하면 계정과 '기본' 카테고리 1개가 함께 생성된다(R6). 둘 중 하나라도 실패하면 둘 다 생성되지 않는다(트랜잭션).
- [ ] 이미 가입된 이메일(대소문자 무시)로 가입하면 실패하고 중복 안내 메시지를 보여준다(R16). **[확정: 이메일 비교는 소문자 정규화]**
- [ ] 이메일 형식이 틀리거나 비밀번호가 8자 미만이면 가입이 거부된다. **[확정]**
- [ ] DB에는 비밀번호 평문이 저장되지 않는다(해시만, 5.2).
- [ ] 로그인 실패 시 이메일 존재 여부를 드러내지 않는 동일 메시지를 보여준다. **[확정]**
- [ ] 인증 없이 회원가입·로그인 외 API를 호출하면 401을 받고, 화면은 로그인 페이지로 이동한다(R1).
- [ ] 로그아웃 후 보호된 화면·API에 접근할 수 없다(UC-03).

#### FR-02 카테고리별 할일 등록 (P0) — R6–R11 / UC-05, UC-06
- [ ] 카테고리를 지정하지 않고 할일을 등록하면 기본 카테고리에 속한다(R7).
- [ ] Given 카테고리 'Work'가 있을 때 When ' work '로 등록하면 Then 중복으로 거부된다(R10).
- [ ] 공백만으로 된 이름은 거부된다(R11).
- [ ] 기본 카테고리의 삭제·이름 변경 요청은 거부된다(R8).
- [ ] 카테고리를 삭제하면 그 안의 할일이 모두 기본 카테고리로 옮겨지고 할일 수는 변하지 않는다(R9, 한 트랜잭션).
- [ ] 다른 사용자의 카테고리 ID로 조회·수정·삭제·할일 지정을 하면 '없음'으로 처리된다(R2, R7).

#### FR-03 내 정보 수정 (P1) — R17 / UC-04
- [ ] 이름, 비밀번호, 시간대를 수정할 수 있다. 이메일은 수정 UI·API가 없다.
- [ ] 비밀번호 변경 시 현재 비밀번호가 틀리면 거부된다.
- [ ] 시간대를 바꾸면 이후 모든 일시 표시와 '오늘' 판정(R4)이 새 시간대 기준이 된다(R5). 시간대는 IANA 이름 목록에서 고른다. **[확정]**
- [ ] 다른 사용자의 프로필은 수정할 수 없다.

#### FR-04 시작·종료 일시 지정 (P0) — R3–R5 / UC-06
- [ ] 시작·종료 날짜를 달력 위젯으로 고르고, 시각(시:분)은 선택 입력이다.
- [ ] 시각을 비우면 시작 00:00, 종료 23:59로 저장된다(R5).
- [ ] Given 오늘이 11/04 When 일시를 모두 비우면 Then 11/04 00:00–11/04 23:59로 저장된다(R4).
- [ ] 시작만 입력하면 종료 = 시작 날짜 23:59, 종료만 입력하면 시작 = min(오늘 00:00, 종료)(R4).
- [ ] 종료 < 시작이면 거부되고, 같으면 허용된다(R3). 검증은 클라이언트와 서버 모두에서 한다(서버가 최종).

#### FR-05 목록 필터링 (P0) — S1–S4, F1–F4 / UC-07
- [ ] 각 할일에 상태(시작 전/진행 중/완료/기한 초과)가 표시되며 S1–S4 순서로 판정된다.
- [ ] Given 종료 11/05 23:59인 미완료 할일 When 현재 11/05 23:59:30 Then 진행 중, When 11/06 00:00 Then 기한 초과(5.3, R5).
- [ ] 종료 일시가 지난 뒤 완료한 할일은 '완료' 필터에만 나온다(5.4).
- [ ] 기한 초과 할일은 '진행 중' 필터에 나오지 않는다(5.4).
- [ ] 카테고리 + 상태 필터를 함께 고르면 AND로 적용된다(F3). 아무것도 고르지 않으면 볼 수 있는 전체가 나온다.
- [ ] 상태 필터는 서버(SQL)에서 적용한 뒤 페이지네이션한다. 페이지마다 개수가 어긋나지 않는다.

#### FR-06 할일 삭제 (P0) — R2, R12, R19 / UC-10
- [ ] 삭제 전 확인 대화상자를 띄운다. **[확정]**
- [ ] 삭제는 영구 삭제이며 같은 ID로 다시 조회하면 '없음'이다(R12). 공유와 이력(FR-10 구현 후)도 함께 삭제된다(R20).
- [ ] 볼 수 없는 할일 삭제 요청은 '없음'(404)으로 응답한다(R2).

#### FR-07 할일 수정·완료 (P0) — R2–R5, R7, R13, R14, R19 / UC-08, UC-09
- [ ] 편집 화면에서 제목·설명·시작/종료 일시·완료 여부를 수정할 수 있고, 수정 시에도 R3을 검증한다.
- [ ] 카테고리를 바꾸지 않으면 기존 카테고리가 유지된다(R7).
- [ ] 목록·편집 화면에서 완료 체크·해제가 가능하다. 시작 전 할일도 완료할 수 있다(R14).
- [ ] 완료 시 `completedAt`이 기록되고, 해제 시 비워진다.
- [ ] 제목이 비어 있으면 저장되지 않는다.

#### FR-08 캘린더 표시 (P0) — R15 / UC-11
- [ ] 월·주·일 뷰를 전환할 수 있고, 이전/다음/오늘 이동이 가능하다.
- [ ] Given 11/03–11/05 할일 When 월 뷰 Then 11/03, 11/04, 11/05 세 칸 모두에 표시된다(R15).
- [ ] 뷰 범위와 하루라도 겹치는 할일은 모두 표시된다(예: 10/30–11/02 할일은 11월 월 뷰에 나온다).
- [ ] 일시는 사용자 시간대(MVP는 KST)로 표시된다(R5).
- [ ] 캘린더의 할일을 누르면 편집 화면으로 이동한다.

#### FR-11 팀 단위 공유 (P0) — R2, R21 / UC-06, UC-08
- [ ] 할일 등록·수정 시 소유자는 자기가 속한 팀 중에서 공유 팀을 여러 개 고를 수 있다. 속하지 않은 팀 ID는 거부된다.
- [ ] 공유 팀 없이 만든 할일은 소유자만 볼 수 있다.
- [ ] 목록·캘린더에서 특정 팀을 고른 상태로 할일을 만들면 공유 팀 기본값이 그 팀이다("팀에서 만든 할일"의 해석). **[확정]**
- [ ] 소유자가 아닌 사용자(관리자 포함)는 공유 팀을 바꿀 수 없다.
- [ ] 구성원이 팀에서 제거되면 그 사람 할일의 그 팀 공유가 해제되어, 다른 구성원에게 더 이상 보이지 않는다.
- [ ] 할일 상세의 공유 팀 목록에는 보는 사람이 속한 팀만 표시된다.

#### FR-09 팀 조회·관리 권한 (P0) — R2, R18, R19, F4 / UC-06–UC-11, UC-13, UC-14
- [ ] 팀을 만들면 만든 사람이 소유자(OWNER)가 된다(UC-13).
- [ ] 소유자만 이메일로 구성원 추가(수락 절차 없음)·제거, 관리자 지정·해제를 할 수 있다(UC-14). 없는 이메일은 '사용자 없음' 오류.
- [ ] 같은 팀 구성원은 그 팀에 공유된 할일을 목록·캘린더에서 볼 수 있으며, 그 할일의 카테고리는 보이지 않는다(R2).
- [ ] 관리자(소유자 포함)는 그 팀에 공유된 다른 구성원의 할일을 등록·수정·삭제·완료 처리할 수 있다(R19).
- [ ] 관리자가 구성원 할일을 등록하면 소유자 = 그 구성원, 카테고리 = 그 구성원의 기본 카테고리, 공유 팀 = 그 팀이다(R19).
- [ ] 일반 팀원이 볼 수 있는 남의 할일을 변경하려 하면 403(권한 없음), 볼 수 없는 할일은 404로 응답한다. **[확정]**
- [ ] F4: 팀 하나 / 사용자 하나 / 팀 전체(기본값)를 고를 수 있고 목록·캘린더 모두에 적용된다.

#### FR-10 변경 이력 (P1) — R20 / UC-12
- [ ] 등록·수정·완료·완료 해제마다 이력 1건(action, 변경자, 일시, 필드별 이전→새 값, 공유 팀 변경 포함)이 생긴다.
- [ ] 이력은 할일 변경과 같은 트랜잭션에서 기록된다(변경 성공 = 이력 존재). **[확정]**
- [ ] 이력의 수정·삭제 API는 없다.
- [ ] 할일을 볼 수 있는 사용자는 이력을 볼 수 있고, 카테고리 변경 내용은 소유자에게만 보인다.
- [ ] 할일을 삭제하면 이력도 삭제된다.

## 5. 비기능 요구사항

### 5.1 성능·확장성 (1000 동시 접속)
| 항목 | 요구사항 | 근거 |
|------|----------|------|
| 배포 구성 | **Vercel**: 프론트엔드 정적 빌드 + Express API(Vercel Functions, 서버리스)를 한 프로젝트·한 도메인(`/api/*`)에 배포 **[확정]**(Q1). PostgreSQL 17은 **Supabase**를 쓴다 **[확정]**(B1). Supabase는 PostgreSQL DB로만 쓰고, Supabase Auth·자동 생성 API는 쓰지 않는다(인증은 5.2의 JWT, DB 접근은 Express + `pg`) | Vercel은 PostgreSQL을 직접 호스팅하지 않는다. 기술 제약(Express + `pg`)을 지키기 위해 BaaS 기능은 쓰지 않는다. 서버리스는 요청량에 따라 인스턴스가 자동으로 늘어난다 |
| 커넥션 풀 | `pg.Pool`은 모듈 최상위에서 한 번만 만들고 `max: 5`, `idleTimeoutMillis: 10000`, `connectionTimeoutMillis: 5000`. Supabase 커넥션 풀러(Supavisor) **트랜잭션 모드** 연결 문자열(포트 6543)로 연결한다 **[확정]** | 서버리스는 인스턴스마다 풀이 생겨 연결 수가 인스턴스 수만큼 곱해진다. 풀러 없이 직접 연결하면 `max_connections`를 넘는다 |
| 풀러 호환 | 이름 있는 prepared statement(`pg`의 `name` 옵션)를 쓰지 않는다. 트랜잭션은 한 요청 안에서 끝낸다 **[확정]** | 트랜잭션 모드 풀러는 세션 상태를 유지하지 않는다 |
| 커넥션 반납 | 트랜잭션은 `pool.connect()` 후 `finally`에서 `release()`. 단건 쿼리는 `pool.query()` | 커넥션 누수 = 동시 접속 시 전체 장애 |
| 인덱스 | 수준만 정한다(DDL은 다음 문서): 사용자 이메일(소문자) 유일, 카테고리 (소유자, 정규화 이름) 유일, 할일 (소유자, 시작·종료 일시), 할일 공유 (팀, 할일), 팀 구성원 (사용자), 이력 (할일, 일시) | 목록·캘린더·권한 확인 쿼리가 모두 인덱스를 타도록 |
| 페이지네이션 | 목록: limit/offset, 기본 50건·최대 100건, 정렬 시작 일시 오름차순 **[확정]** | 응답 크기 상한 |
| 캘린더 조회 | 기간 범위 쿼리(최대 42일 = 월 뷰 6주), 결과 상한 500건 **[확정]** | 월 뷰도 유한한 범위로 제한 |
| 상태 계산 | 상태(S1–S4)는 SQL에서 현재 일시(분 단위 절삭)로 계산해 필터·정렬에 사용 | 저장하지 않음(5.1장 도메인). 페이지네이션 정확성 |
| N+1 금지 | 목록 1회 조회에 공유 팀 등 연관 데이터를 JOIN/집계로 함께 가져온다 | 쿼리 수 = 요청당 상수 |
| 부하 테스트 | 하지 않는다 **[확정]**(Q2) | 일정 우선. 위 설계 원칙으로 위험을 줄인다(K3) |

### 5.2 보안
| 항목 | 요구사항 | 근거 |
|------|----------|------|
| 비밀번호 저장 | bcrypt, cost 10 **[확정]**. 라이브러리는 순수 JS인 `bcryptjs` **[확정]** | 업계 표준. cost 10은 해시 1회 약 50–100ms로 로그인 부하(M3)와 균형. 네이티브 `bcrypt`는 서버리스 빌드에서 바이너리 문제가 생길 수 있다 |
| 인증 방식 | **JWT 권장**: 로그인 시 서명된 JWT를 `httpOnly`, `Secure`, `SameSite=Lax` 쿠키로 발급, 만료 24시간, 리프레시 토큰 없음. 로그아웃 = 쿠키 삭제 **[확정]** | 서버에 세션 저장소가 필요 없어 요청마다 DB 조회가 없고(1000 동시 접속과 서버리스에 유리), 1인·2일 구현이 단순. 권한(R2, R19)은 토큰에 담지 않고 매 요청 DB로 확인하므로 팀 역할 변경이 즉시 반영됨. `httpOnly` 쿠키로 XSS 토큰 탈취 방지 |
| 인증 한계 | 로그아웃 후에도 탈취된 토큰은 만료까지 유효 | 만료 24시간으로 제한. 필요 시 v1.x에서 세션/리프레시 토큰 도입 |
| SQL 인젝션 | 모든 쿼리는 `pg` parameterized query(`$1, $2 …`)만 사용. 문자열 연결로 SQL을 만들지 않는다. 정렬 컬럼 등 식별자는 화이트리스트로만 선택 | Prisma 미사용이므로 직접 보장해야 함 |
| 접근 제어(R2) | 할일·카테고리 조회/변경 쿼리의 WHERE 절에 권한 조건(소유자 또는 공유 팀 구성원/관리자)을 포함. 권한 없는 리소스는 404(존재 비노출), 볼 수는 있으나 변경 권한이 없으면 403 | 클라이언트 숨김에 의존하지 않고 서버가 최종 판정 |
| 카테고리 노출 | 다른 사람 할일 응답에서 카테고리 필드를 제거(R2) | 서버 응답 단계에서 보장 |
| 입력 검증 | 모든 입력을 서버에서 검증(필수값, 길이, 일시 형식, R3). 요청 본문 크기 제한 **[확정: 100KB]** | 신뢰 경계 |
| 전송 | 운영 환경 HTTPS 필수 (Vercel 기본 제공) | 쿠키 `Secure` 전제 |
| CSRF | `SameSite=Lax` 쿠키 + 상태 변경은 GET 금지 + 프론트·API 동일 출처(Vercel 한 프로젝트, `/api/*`) **[확정]** | 별도 CSRF 토큰 없이 기본 방어 |
