## 1. 개요

### 1.1 제품 비전
기간(시작·종료 일시)이 있는 할일을 개인별로 관리하고, 팀과 공유해 캘린더(월·주·일)에서 한눈에 보며, 누가 무엇을 바꿨는지 추적할 수 있는 웹 TodoList.

### 1.2 배경 / 해결할 문제
| 문제 | 해결 FR |
|------|---------|
| P1 개인별 인증 할일 관리 부재 | FR-01, FR-02, FR-03, FR-06, FR-07 |
| P2 기간 지정 관리 불가 | FR-04, FR-05 |
| P3 캘린더 통합 조회 불가 | FR-08 |
| P4 팀 일정 공유·관리 불가 | FR-09, FR-11 |
| P5 변경 추적 불가 | FR-10 |

### 1.3 목표 사용자
| 구분 | 설명 |
|------|------|
| 학생 | 과제·시험 등 기간이 있는 일정을 관리. 스터디·조별 과제 팀 공유 |
| 직장인 (20대–50대) | 업무 일정 관리, 팀 단위 일정 공유. 팀장은 관리자(R19)로 팀원 일정 관리 |

- 사용자 페르소나별 상세 시나리오는 작성하지 않는다(사용자 요청). 기능 흐름 단위 시나리오는 `docs/3-user-scenario.md`에 있다.

## 2. 목표 및 성공 지표

### 2.1 비즈니스 목표
- 동시 접속 사용자 1000명이 지연·오류 없이 사용할 수 있어야 한다.
- 2일 내(2026-11-04 수 – 11-05 목) 1인 개발로 핵심 기능(MVP, 4장 P0)과 P1을 완성한다(Q3).

### 2.2 부하 모델 **[확정]**
| 항목 | 값 | 근거 |
|------|----|------|
| 동시 접속 | 1000명 (가상 사용자 1000 VU) | 비즈니스 목표 |
| 사용자당 요청 간격(think time) | 평균 10초 (5–15초) | 할일 앱은 화면 조회 후 입력·확인에 시간이 걸린다 |
| 평균 처리량 | 약 100 RPS | 1000명 ÷ 10초 |
| 검증 처리량 | 200 RPS (평균의 2배) | 출근·수업 시작 시각 몰림 대비 |
| 요청 구성 | 조회(목록·캘린더) 70% / 쓰기(등록·수정·완료·삭제) 20% / 인증 10% | 일반적인 CRUD 앱의 읽기 위주 패턴 |

- 부하 테스트는 하지 않는다(Q2). 이 모델은 설계(커넥션·인덱스·페이지네이션, 5.1)의 근거로만 쓴다.

### 2.3 성공 지표 (KPI)
| ID | 지표 | 목표 | 측정 방법 | 근거 |
|----|------|------|-----------|------|
| M1 | 조회 API p95 응답시간 (목록·캘린더) | ≤ 500ms | 설계 목표. 부하 테스트 생략(Q2)으로 출시 전 실측하지 않음 | 사용자가 지연을 체감하지 않는 일반 기준 |
| M2 | 쓰기 API p95 응답시간 | ≤ 800ms | 동일 | 트랜잭션(이력 기록 등) 포함 |
| M3 | 로그인 API p95 응답시간 | ≤ 1500ms | 동일 | 비밀번호 해시 검증이 CPU를 쓴다(5.2) |
| M4 | 오류율 (5xx + 타임아웃) | < 1% | 동일 | 정상 부하에서 서버 오류는 예외적이어야 한다 |
| M5 | DB 커넥션 풀 대기 p95 | < 50ms | 동일 | 풀 크기(5.1)가 충분한지 확인 |
| M6 | P0 수용 기준 통과율 | Day 2 종료 시 100% | 4장 체크리스트 수동/자동 검증 | 2일 MVP 완료 정의 |
| M7 | 신규 가입자 중 24시간 내 할일 1건 이상 등록 비율 | ≥ 70% | DB 집계 | 핵심 가치(할일 등록) 도달 여부 **[확정]** |

- M1–M5 수치는 모두 **[확정]**이다. 단, 부하 테스트를 생략하므로(Q2) 1000명 동시 접속 달성 여부는 출시 전에 검증되지 않는다(K3).

## 3. 범위

| 프로필 | 이름·비밀번호·시간대 수정 | FR-03 / UC-04 |

| 조회 | 목록 필터(팀·사용자 / 카테고리 / 상태), 캘린더(월·주·일) | FR-05, FR-08 / UC-07, UC-11 |
| 팀 | 팀 생성, 구성원·역할 관리, 할일 팀 공유, 관리자 권한 | FR-09, FR-11 / UC-13, UC-14 |

### 3.2 Out of Scope
- 도메인 정의서 7장 전체(팀 삭제·소유자가 아닌 구성원의 팀 나가기·나가기와 무관한 소유자 위임·초대 수락, 삭제 할일 이력·되돌리기, 알림·리마인더, 반복 할일, 종일/시간 구분, 우선순위·태그·하위 할일·첨부, 소셜 로그인·비밀번호 찾기·이메일 인증, 회원 탈퇴, 휴지통, 외부 캘린더 연동, 통계·리포트).
- PRD 추가 제외:
  - 네이티브 모바일 앱 (반응형 웹만)
  - 접근성(WCAG 등) 대응 (사용자 요청으로 고려하지 않음)
  - 다국어 (한국어 UI만) **[확정]**
  - 실시간 동기화(WebSocket 등). 다른 사용자의 변경은 새로고침·재조회 시 반영 **[확정]**

- FR-09 중 소유자의 팀 나가기(다음 소유자 지정, R18)는 P1이다 **[확정]**(사용자 시나리오 C-11).
- 권한 조건(R2, R19, R21)은 처음부터 목록·캘린더·수정·삭제 쿼리에 넣는다. 개인용으로 먼저 만들고 나중에 고치지 않는다.

### 4.3 FR별 요구사항 및 수용 기준

#### FR-01 회원가입·로그인 (P0) — R1, R6, R16 / UC-01–UC-03
- [ ] 이메일·비밀번호·이름으로 가입하면 계정과 '기본' 카테고리 1개가 함께 생성된다(R6). 둘 중 하나라도 실패하면 둘 다 생성되지 않는다(트랜잭션).
- [ ] 이미 가입된 이메일(대소문자 무시)로 가입하면 실패하고 중복 안내 메시지를 보여준다(R16).
- [ ] 이메일 형식이 틀리거나 비밀번호가 8자 미만이거나 UTF-8 72바이트를 넘으면 가입이 거부된다(도메인 정의서 3.4).
- [ ] DB에는 비밀번호 평문이 저장되지 않는다(해시만, 5.2).
- [ ] 로그인 실패 시 이메일 존재 여부를 드러내지 않는 동일 메시지를 보여준다. **[확정]**
- [ ] 인증 없이 회원가입·로그인·토큰 갱신·로그아웃 외 API를 호출하면 401을 받고, 화면은 로그인 페이지로 이동한다(R1). 토큰 갱신과 로그아웃은 액세스 토큰이 만료된 상태에서도 호출되므로 인증 없이 받는다(5.2). 공개 경로 전체 목록(배포 확인용 헬스 체크 포함, K10)은 `docs/5-project-principle.md` SEC-04를 따른다.
- [ ] 로그아웃 후 그 브라우저에서는 보호된 화면·API에 접근할 수 없다(서버가 리프레시 토큰을 폐기하고 쿠키 삭제, UC-03). 이미 탈취된 액세스 토큰은 만료(최대 15분)까지 유효하다(5.2 인증 한계).
- [ ] 가입에 성공하면 바로 로그인되어(인증 쿠키 발급) 할일 목록(SC-03)으로 이동한다. 로그인 후 첫 화면도 SC-03이다(R16, UC-01). **[확정]**
- [ ] 로그인할 때 이메일 대소문자를 구분하지 않는다(R16). **[확정]**
- [ ] 액세스 토큰(15분)이 만료돼도 리프레시 토큰(7일)이 유효하면 다시 로그인하지 않고 화면을 계속 쓸 수 있다. 리프레시 토큰이 만료·폐기되었거나 이미 쓴 토큰을 다시 쓰면 401이고 로그인 화면으로 이동한다(5.2). **[확정]**

#### FR-02 카테고리별 할일 등록 (P0) — R6–R11 / UC-05, UC-06
- [ ] 카테고리를 지정하지 않고 할일을 등록하면 기본 카테고리에 속한다(R7).
- [ ] Given 카테고리 'Work'가 있을 때 When ' work '로 등록하면 Then 중복으로 거부된다(R10).
- [ ] 공백만으로 된 이름은 거부된다(R11).
- [ ] 기본 카테고리의 삭제·이름 변경 요청은 거부된다(R8).
- [ ] 카테고리를 삭제하면 그 안의 할일이 모두 기본 카테고리로 옮겨지고 할일 수는 변하지 않는다(R9, 한 트랜잭션).
- [ ] 다른 사용자의 카테고리 ID로 조회·수정·삭제·할일 지정을 하면 '없음'으로 처리된다(R2, R7).
- [ ] 카테고리 삭제 전 확인 대화상자를 띄운다. 취소하면 아무것도 바뀌지 않는다. **[확정]**

#### FR-03 내 정보 수정 (P1) — R17 / UC-04
- [ ] 이름, 비밀번호, 시간대를 수정할 수 있다. 이메일은 수정 UI·API가 없다.
- [ ] 비밀번호 변경 시 현재 비밀번호가 틀리면 거부된다.
- [ ] 시간대를 바꾸면 이후 모든 일시 표시와 '오늘' 판정(R4)이 새 시간대 기준이 된다(R5). 시간대는 IANA 이름 목록에서 고른다. **[확정]**
- [ ] 다른 사용자의 프로필은 수정할 수 없다.
- [ ] 비밀번호를 바꾸면 그 사용자의 다른 브라우저 로그인(리프레시 토큰)이 모두 해제되고, 변경한 브라우저는 로그인 상태를 유지한다(5.2). **[확정]**

#### FR-04 시작·종료 일시 지정 (P0) — R3–R5 / UC-06
- [ ] 시작·종료 날짜를 달력 위젯으로 고르고, 시각(시:분)은 선택 입력이다.
- [ ] 시각을 비우면 시작 00:00, 종료 23:59로 저장된다(R5).
- [ ] Given 오늘이 11/04 When 일시를 모두 비우면 Then 11/04 00:00–11/04 23:59로 저장된다(R4).
- [ ] 시작만 입력하면 종료 = 시작 날짜 23:59, 종료만 입력하면 시작 = min(오늘 00:00, 종료)(R4).
- [ ] 종료 < 시작이면 거부되고, 같으면 허용된다(R3). 검증은 클라이언트와 서버 모두에서 한다(서버가 최종).

#### FR-05 목록 필터링 (P0) — S1–S4, F1–F4 / UC-07
- [ ] 각 할일에 상태(시작 전/진행 중/완료/기한 초과)가 표시되며 S1–S4 순서로 판정된다.
- [ ] Given 종료 11/05 23:59인 미완료 할일 When 현재 11/05 23:59:30 Then 진행 중, When 11/06 00:00 Then 기한 초과(5.3, R5).
- [ ] 종료 일시가 지난 뒤 완료한 할일은 '완료' 필터에만 나온다(5.4).
- [ ] 기한 초과 할일은 '진행 중' 필터에 나오지 않는다(5.4).
- [ ] 카테고리 + 상태 필터를 함께 고르면 AND로 적용된다(F3). 아무것도 고르지 않으면 볼 수 있는 전체가 나온다.
- [ ] 상태 필터는 서버(SQL)에서 적용한 뒤 페이지네이션한다. 페이지마다 개수가 어긋나지 않는다.

#### FR-06 할일 삭제 (P0) — R2, R12, R19 / UC-10
- [ ] 삭제 전 확인 대화상자를 띄운다. **[확정]**

#### FR-11 팀 단위 공유 (P0) — R2, R21 / UC-06, UC-08
- [ ] 할일 등록·수정 시 소유자는 자기가 속한 팀 중에서 공유 팀을 여러 개 고를 수 있다. 속하지 않은 팀 ID는 거부된다.
- [ ] 공유 팀 없이 만든 할일은 소유자만 볼 수 있다.
- [ ] 등록 화면에서는 먼저 어느 팀 할일인지 고른다. 목록·캘린더에서 특정 팀을 고른 상태로 만들면 그 팀이, 그 밖에는 '없음(개인 할일)'이 기본값이고, 고른 팀이 공유 팀 기본값이다(R19, R21). **[확정]**
- [ ] 소유자가 아닌 사용자(관리자 포함)는 공유 팀을 바꿀 수 없다.
- [ ] 구성원이 팀에서 제거되면 그 사람 할일의 그 팀 공유가 해제되어, 다른 구성원에게 더 이상 보이지 않는다.
- [ ] 할일 상세의 공유 팀 목록에는 보는 사람이 속한 팀만 표시된다.

#### FR-09 팀 조회·관리 권한 (P0) — R2, R18, R19, F4 / UC-06–UC-11, UC-13, UC-14
- [ ] 팀을 만들면 만든 사람이 소유자(OWNER)가 된다(UC-13).
- [ ] 소유자만 이메일로 구성원 추가(수락 절차 없음)·제거, 관리자 지정·해제를 할 수 있다(UC-14). 없는 이메일은 '사용자 없음' 오류.
- [ ] 같은 팀 구성원은 그 팀에 공유된 할일을 목록·캘린더에서 볼 수 있으며, 그 할일의 카테고리는 보이지 않는다(R2).
- [ ] 관리자(소유자 포함)는 그 팀에 공유된 다른 구성원의 할일을 등록·수정·삭제·완료 처리할 수 있다(R19).
- [ ] 관리자가 구성원 할일을 등록하면 소유자 = 그 구성원, 카테고리 = 그 구성원의 기본 카테고리, 공유 팀 = 그 팀이다(R19).
- [ ] 일반 팀원이 볼 수 있는 남의 할일을 변경하려 하면 403(권한 없음), 볼 수 없는 할일은 404로 응답한다. **[확정]**
- [ ] F4: 팀 하나 / 사용자 하나 / 팀 전체(기본값)를 고를 수 있고 목록·캘린더 모두에 적용된다.
- [ ] 구성원을 추가할 때 역할(관리자/일반 팀원)을 고를 수 있고, 고르지 않으면 일반 팀원이다. 이미 구성원인 이메일은 거부된다(R18). **[확정]**
- [ ] 팀 이름은 시스템 전체에서 중복될 수 없다(앞뒤 공백 제거, 대소문자 무시, R18). **[확정]**
- [ ] 등록 화면에서 고른 팀의 관리자일 때만 소유자를 고를 수 있고, 선택지는 그 팀 구성원(기본값 본인)이다. 그 팀 비구성원을 소유자로 지정하면 400 `INVALID_OWNER`로 거부되고, 그 팀의 관리자가 아닌 일반 팀원이 API로 다른 사람을 소유자로 지정하면 403 `FORBIDDEN`이다(R19). **[확정]**
- [ ] F4 사용자 필터에서 고를 수 있는 사용자는 내가 속한 팀들의 구성원이다. **[확정]**
- [ ] [P1] 소유자는 다음 소유자를 다른 구성원 중에서 지정해야 팀을 나갈 수 있다. 위임·제거·그 사람 할일의 팀 공유 해제는 한 트랜잭션이다. 다른 구성원이 없거나 지정 없이 자신을 제거하려 하면 거부된다(R18, R21). 검사 순서는 다른 구성원 없음(409 `NO_NEXT_OWNER`) → 다음 소유자 미지정(409 `OWNER_MUST_TRANSFER`)이고, 지정한 사람이 그 팀의 다른 구성원이 아니면 400 `INVALID_OWNER`, 소유자가 아닌 구성원의 요청은 403 `FORBIDDEN`이다. 소유자의 자기 제거는 팀 나가기로만 처리하며, 구성원 제거 API로 자기 자신을 지정하면 400 `VALIDATION_ERROR`다. **[확정]**

#### FR-10 변경 이력 (P1) — R20 / UC-12
- [ ] 등록·수정·완료·완료 해제마다 이력 1건(action, 변경자, 일시, 필드별 이전→새 값, 공유 팀 변경 포함)이 생긴다. 요청 1건에 이력 1건이며, 완료 여부가 바뀐 요청은 `COMPLETED`/`UNCOMPLETED`, 그 밖은 `UPDATED`이고 함께 바뀐 필드도 모두 `changes`에 담는다(R20). **[확정]**
- [ ] 이력은 할일 변경과 같은 트랜잭션에서 기록된다(변경 성공 = 이력 존재). **[확정]**
- [ ] 이력의 수정·삭제 API는 없다.
- [ ] 할일을 볼 수 있는 사용자는 이력을 볼 수 있고, 카테고리 변경 내용은 소유자에게만 보인다.
- [ ] 할일을 삭제하면 이력도 삭제된다.
- [ ] 이력 속 공유 팀 변경은 보는 사람이 속한 팀만 보이고, 걸러낸 뒤 보여줄 변경이 없는 이력은 숨긴다(R20, R21). **[확정]**

### 5.2 보안
| 항목 | 요구사항 | 근거 |
|------|----------|------|
| 비밀번호 저장 | bcrypt, cost 10 **[확정]**. 라이브러리는 순수 JS인 `bcryptjs` **[확정]** | 업계 표준. cost 10은 해시 1회 약 50–100ms로 로그인 부하(M3)와 균형. 네이티브 `bcrypt`는 서버리스 빌드에서 바이너리 문제가 생길 수 있다 |
| 인증 방식 | **액세스 토큰 + 리프레시 토큰** **[확정]**(A18, A25, A26): ① 액세스 토큰은 `HS384`로 서명한 JWT, 만료 15분, 쿠키 `access_token`. ② 리프레시 토큰은 무작위 불투명 문자열, 7일 절대 만료(갱신해도 연장 안 함), DB에는 해시만 저장, 쿠키 `refresh_token`(`Path=/api/auth`). 두 쿠키 모두 `httpOnly`, `Secure`, `SameSite=Lax`(프론트와 API가 서로 다른 사이트로 배포되면 `None`). ③ `POST /api/auth/refresh`로 갱신할 때마다 새 리프레시 토큰을 주고 쓴 토큰은 폐기한다(회전). 이미 폐기된 토큰이 다시 오면 그 사용자의 리프레시 토큰을 모두 폐기한다(재사용 감지). ④ 로그아웃은 리프레시 토큰 폐기 + 쿠키 삭제, 비밀번호 변경은 그 사용자의 리프레시 토큰 전체 폐기. ⑤ 서명 키 `JWT_SECRET`은 48바이트 이상, 검증 알고리즘은 `HS384` 하나로 고정 | 보호 API는 액세스 토큰 검증만 하므로 요청마다 DB 조회가 없다(1000 동시 접속과 서버리스에 유리). DB 조회는 15분에 한 번 갱신할 때만 생긴다. 액세스 토큰 만료를 짧게 해 탈취 피해를 줄이고, 리프레시 토큰은 서버에서 폐기할 수 있다. 권한(R2, R19)은 토큰에 담지 않고 매 요청 DB로 확인하므로 팀 역할 변경이 즉시 반영됨. `httpOnly` 쿠키로 XSS 토큰 탈취 방지. 알고리즘 고정으로 `alg` 바꿔치기 방지 |
| 인증 한계 | 로그아웃·비밀번호 변경 후에도 이미 탈취된 액세스 토큰은 만료(최대 15분)까지 유효. 여러 탭이 거의 동시에 갱신하면 늦은 쪽이 재사용으로 판정되어 로그아웃될 수 있다(K11) | 액세스 토큰 15분으로 제한 |
| SQL 인젝션 | 모든 쿼리는 `pg` parameterized query(`$1, $2 …`)만 사용. 문자열 연결로 SQL을 만들지 않는다. 정렬 컬럼 등 식별자는 화이트리스트로만 선택 | Prisma 미사용이므로 직접 보장해야 함 |
| 접근 제어(R2) | 할일·카테고리 조회/변경 쿼리의 WHERE 절에 권한 조건(소유자 또는 공유 팀 구성원/관리자)을 포함. 권한 없는 리소스는 404(존재 비노출), 볼 수는 있으나 변경 권한이 없으면 403 | 클라이언트 숨김에 의존하지 않고 서버가 최종 판정 |
| 카테고리 노출 | 다른 사람 할일 응답에서 카테고리 필드를 제거(R2) | 서버 응답 단계에서 보장 |
| 입력 검증 | 모든 입력을 서버에서 검증(필수값, 길이, 일시 형식, R3). 길이 상한은 도메인 정의서 3.2–3.6(이메일 254, 비밀번호 8자 이상·UTF-8 72바이트 이하, 이름·카테고리·팀 이름 50, 제목 200, 설명 2,000자). 요청 본문 크기 제한 **[확정: 100KB]** | 신뢰 경계 |
| 오류 응답 | 본문 `{ "error": { "code", "message" } }`. 상태 코드·코드·한국어 메시지 목록은 사용자 시나리오 6.2를 따른다. 현재 비밀번호 오류는 400(401은 로그인 화면 이동 신호) **[확정]** | 프론트엔드가 코드로 분기, 메시지는 그대로 표시 |
| 전송 | 운영 환경 HTTPS 필수 (Vercel 기본 제공) | 쿠키 `Secure` 전제 |
| CSRF | `SameSite=Lax` 쿠키(다른 사이트 배포면 `None`) + 상태 변경은 GET 금지 + CORS 허용 목록 밖 출처의 상태 변경 요청 거부(Origin 검사) **[확정]**(2026-11-05 변경, 당초 동일 출처) | 별도 CSRF 토큰 없이 기본 방어. Origin 검사는 `SameSite=None`에서도 유효 |

### 5.3 시간대 처리 (R5)
| 항목 | 요구사항 |
|------|----------|
| 저장 | `timestamptz` 컬럼, DB 세션 시간대 `Asia/Seoul`로 KST 기준 처리. 커넥션 풀러(트랜잭션 모드)는 연결별 `SET`을 유지하지 않으므로 `ALTER DATABASE … SET timezone TO 'Asia/Seoul'`로 DB 기본값을 고정하고 코드에서 `SET TIME ZONE`을 하지 않는다 **[확정]**(A28) |
| API 형식 | ISO 8601 + 오프셋(예: `2026-11-04T09:00+09:00`) **[확정]**. 예외로 시각을 입력하지 않은 요청 값은 날짜만(`YYYY-MM-DD`) 보내고, 서버가 요청자 `User.timezone` 기준으로 시작 00:00, 종료 23:59를 채운다(R5, `docs/5-project-principle.md` SEC-11) **[확정]** |
| 표시 | 프론트엔드에서 `User.timezone`으로 변환(MVP는 KST 고정) |
| '오늘' 판정 | R4의 '오늘'과 기본 일시는 서버에서 요청자(인증된 사용자)의 `User.timezone` 기준으로 계산. 관리자가 구성원 할일을 대리 등록해도 소유자가 아니라 요청자(관리자)의 시간대를 쓴다 **[확정]** |
| 현재 일시 | 상태 판정 시 서버 현재 일시를 분 단위로 절삭(R5). 클라이언트 시계는 사용하지 않음 |
